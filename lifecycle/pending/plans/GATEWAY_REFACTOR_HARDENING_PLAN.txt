   D24 MCP tool schema read under both spellings. mcp 2.x renamed the
       field to input_schema and kept inputSchema as the wire alias; mcp
       1.x has only inputSchema. The copied domain packages construct
       Tools with the alias, which both versions accept, so only the READ
       needs to tolerate both -- hence registry._tool_schema rather than
       pinning mcp or rewriting nine packages. Consequence: a Tool with
       neither field yields {"type": "object"} and args validation
       becomes a no-op for it, which is deliberately permissive because a
       schemaless tool is a registry bug (caught by
       tests/unit/test_registry.py), not a caller-facing gate.

   D25 The PHI redaction key set is a knowledge file and a loaded file
       REPLACES the fallback. knowledge/policies/
       phi-redaction-fields.data.json is the key set;
       redact._FALLBACK_PHI_KEYS mirrors it for absence. Replacement not
       merge, so the file is auditable as THE answer -- a merge means no
       reader can tell what is enforced without also reading the code.
       The cost is the standing obligation that the file stay a SUPERSET
       of the fallback, asserted by
       tests/invariants/test_phi_redaction_holes.py. Record the
       fail-closed spellings: query (a lookup's search echo IS a name),
       id, chart, memo, zipcode, _text nodes, raw_xml. Consequence: a
       non-PHI caller sees <REDACTED> for a code lookup's echo and a
       masterfile row's internal id; callers needing those carry phi=true.

   D26 raw_xml is a second permission on top of phi, never a substitute.
       The raw string is a whole AMD body and is unredactable, so
       worker.strip_raw_xml removes every raw-XML key (and the
       `<key>_hash` sidecar the Redactor leaves) unless the caller has
       BOTH flags, and OMITS rather than blanks so a caller cannot
       distinguish "stripped" from "never produced". An unresolvable
       caller gets neither flag. Consequence: a --raw-xml token without
       --phi gets nothing, which is the intended trap; and the gate is
       live and tested before any producer exists, which is the right
       order (see R4).

SECTION 5. DEFERRED (NON-BLOCKING)
---------------------------------------------------------------------

5.1 Staff token issued after AMD validation, for console UX

admin-console today uses POST /v1/login only: it forwards a staff
credential to AMD and gets a boolean. A future improvement is that a
SUCCESSFUL /v1/login also mints a short-lived GATEWAY token for that
staff session, so the console can offer per-staff tooling without a
shared service token.

DEFERRED, non-blocking, not in scope of any R-phase. It needs a token
lifetime model the table does not have (every entry today is long-lived
with a revoked flag), a decision on which tools a staff token may call,
and its own compliance pass. None of that gates the migration, and
adding it now would change the SPEC 10.1 token-table shape that eight
consumers are about to depend on. REVISIT after the consumer plan's
PHASE 2, when the console's real UX need is observable.

5.2 NEVER: per-user AMD sessions

Not a deferral -- a permanent NO, and the single most important thing a
future reader must not "improve". The gateway holds ONE AdvancedMD
session, keyed on ONE office key, paced by ONE rate clock, in ONE
process, with ONE replica (SPEC 4.5, 4.6, 4.7, 10.5, 21). AMD's caps are
PER OFFICE KEY, it bills $0.01 per excess call, and it refuses logins
faster than roughly once a minute. A per-user session means N logins
against a one-per-minute bucket and N clocks against one cap -- exactly
the failure the gateway was built to end. A staff token (5.1) is a
GATEWAY-side credential over the shared AMD session; it is not, and
must never become, a per-user AMD login. Anything shaped like "give each
user their own AMD session" is rejected without a design review.

  application, one adversarial handoff verification) where a false PASS
  is unrecoverable (a note body delivered to a caller not entitled to
  it), expensive (AMD overage billing), or propagates into another
  plan's live cutover. The five sonnet dispatches are documentation,
  scripts, and worksheets.

  ZERO fable: nothing here is frontier reasoning -- the design decisions
  are already made in SPEC.md and R4.3. What is needed is care and
  refusal to hand-wave, which opus supplies.
  ZERO haiku: there is no trivial edit. Every file touched is a PHI
  gate, a verification table, or a document another plan's gate reads.

6.4 Estimated wall-clock

  AGENT time with parallelism: ~4-6 hours of dispatches.
  OPERATOR time is the binding constraint and is not compressible:
    R1  24 h /health watch (mostly unattended) + ~1 h of service setup,
        token issuance, and the SIGHUP drill
    R2  two AMD sessions; tier-1 and tier-3 pacing plus the
        review-on-the-box step means ~1-2 h each, not minutes
    R3  one scheduled load window, multi-minute run plus a mid-load
        restart, ~1-2 h including analysis review
    R5  signature

  CRITICAL PATH: R0 -> R1.0 -> R1 (the 24 h watch, irreducible) -> R2a
  -> R2.post -> R4.c -> R4.g -> R5. Elapsed time is dominated by the
  watch and by scheduling the operator's two AMD sessions and one load
  window. Realistic: 3-5 calendar days, under a day of which is anybody
  working. R2b is off the critical path for consumer PHASE 0 only if
  H-3's deferred-tool bookkeeping is filled in honestly.

6.5 Failure recovery policy

  R0     retry up to 2x with the same subagent. A red fresh-clone suite
         is a real defect: fix it, re-run, never skip.
  R1.0   compliance BLOCK -> PAUSE AND ESCALATE. Never retry a
         compliance gate with a different model hoping for a better
         verdict; fix the finding, then re-review.
  R1     deploy failure -> retry after fixing the named cause. Climbing
         login refusals -> ESCALATE (AMD-side or legacy contention,
         neither of which an agent can fix).
  R2     a failed live check is a FINDING, not a phase failure: fix that
         tool's request map, leave the row PENDING, continue with the
         others. Escalate only if the map cannot be derived from a
         reference client.
  R3     a failed assertion -> ESCALATE. A cap breach or p95 blowout is
         a gateway design finding (possibly SPEC 25's deferred
         two-in-flight work), not something to retry.
  R4a    code failing its own tests -> retry up to 2x.
  R4b    Compliance BLOCK -> HALT R4, mark H-11 ABSENT, CONTINUE to R5.
         This is the one BLOCK in the plan that is explicitly
         survivable and the handoff must say so. R4a's code may stay in
         main; revoke/withhold --raw-xml on note-audit's token instead
         (the policy-level rollback in R4's ROLLBACK section).
  R5     an unevidenced claim -> return to the phase that produced it.
         Never sign around it.
  DEFAULT for anything unlisted: pause and escalate.

6.6 Audit trail location

  Per-phase evidence: runtime/audits/gateway-hardening/R0.md through
  R4.md. Final rollup (the signed handoff): R5.md. runtime/ is
  gitignored (added in R0). Nothing in these files may contain a
  credential, a token plaintext, an AMD response body, or a patient
  identifier -- counts, dates, verdicts, and endpoint-shaped facts only.
